# BestOW UI 포지셔닝

> 왜 BestOW UI 를 써야 하는가 — 누구를 위해, 무엇을 약속하고, 다른 선택지와 무엇이 다른가.
> 로드맵의 "P6. 차별화" 는 이 문서를 근거로 한다. 사실(경쟁 제품·표준)은 확인한 출처를 함께 적고, 확인하지 못한 것은 **(확인 필요)** 로 표시한다.
> 작성 2026-10-15 · 기준 버전 react·tokens 0.9.0

## 한 줄 정의

**한국 서비스를 만들 때 바로 쓰는, 접근성이 검증된 React 디자인 시스템.**

브랜드 색 하나만 넣으면 라이트·다크 모두 접근성 기준을 지키는 테마가 만들어지고,
약관 동의·인증번호·전화번호·금액처럼 한국 서비스에 늘 필요한 부품이 기본으로 들어 있다.

## 누구를 위한가

| 대상 | 지금 겪는 문제 | BestOW UI 가 주는 것 |
|---|---|---|
| **한국 서비스를 만드는 스타트업·사이드 프로젝트 개발자** (1순위) | 글로벌 DS 에는 약관 동의·인증번호 입력 같은 부품이 없어 매번 직접 만든다. 회사 DS(SEED, Vapor 등)는 그 회사 브랜드에 맞춰져 있다 | 한국 서비스 부품 + 내 브랜드로 바꾸기 쉬운 테마 |
| **웹 접근성을 지켜야 하는 프로젝트** (공공·에이전시·대기업 외주) | 접근성 인증 심사를 앞두고 컴포넌트마다 근거를 따로 정리한다 | 컴포넌트별 KWCAG 2.2 대응 근거 문서 + 자동 검사 결과 |
| 디자이너 없이 만드는 1인 개발자 | 색을 고르면 대비가 깨지고, 다크 모드는 따로 손봐야 한다 | 대표색 하나 → 대비 보장 라이트·다크 테마 |

**하지 않을 것 (non-goals)**
- 특정 회사의 브랜드 표현(일러스트, 고유 모션 등) — 우리는 **브랜드 중립**이고 사용자가 입힌다.
- 모바일 네이티브(iOS·Android) — 웹(React)에 집중한다. 멀티 플랫폼이 필요하면 SEED 같은 선택지가 맞다.
- Tailwind 전용 복사형(shadcn/ui 방식) — 설치해서 쓰는 패키지로 버전 업데이트를 받게 한다.

## 핵심 약속 (차별화 축)

### 1. 한국 서비스 키트 — "한국 서비스에 늘 필요한 부품이 기본으로"

진행: 약관 동의(`AgreementGroup`)·인증번호(`VerificationCodeInput`) 완료 (2026-10-15, Storybook › Korean Kit).

글로벌 DS 에는 없고, 한국 서비스는 거의 매번 직접 만드는 것들. (다른 한국 DS 의 제공 여부는 **(확인 필요)**)

| 부품 | 핵심 동작 | 접근성 포인트 |
|---|---|---|
| 약관 동의 그룹 | 전체 동의 ↔ 개별 동기화, 필수·선택 표시, 약관 펼쳐 보기, 필수 미동의 시 안내 | 전체 동의의 부분 선택(indeterminate) 상태, 그룹 이름, 오류를 aria-describedby 로 |
| 인증번호 입력 | 6칸 입력, 붙여넣기·자동 이동, 남은 시간 타이머, 재전송, 문자 자동 채우기(`autocomplete="one-time-code"`) | 칸마다가 아닌 하나의 이름("인증번호 6자리"), 시간 만료 안내를 스크린리더에 |
| 전화번호·사업자등록번호 입력 | 하이픈 자동 삽입, 사업자번호 검증 공식 | 서식 안내를 레이블과 분리해 describedby 로 |
| 금액 입력 | 천 단위 쉼표, 원/만원 단위, 한글 금액 읽기("12만 5천원") | 화면 표기와 별개로 읽기 쉬운 값(aria-valuetext 등) |
| 주소 검색 | Daum 우편번호 서비스 연동, 기본·상세 주소 분리 | 검색 팝업·레이어의 포커스 이동 |
| 날짜 선택 | 한국어 요일·날짜 표기, (선택) 공휴일 표시 | 달력 격자 키보드 이동 |

### 2. 검증된 접근성 — "주장하지 않고 증명한다"

이미 있는 것:
- 모든 스토리를 **라이트·다크 두 테마에서 axe 로 검사**하고 위반이 있으면 CI 실패 (스토리 312개, 열린 목록·팝업은 `play` 로 연 상태까지).
- 핵심 동작 테스트는 구현을 일부러 망가뜨려 실제로 잡아내는지 확인(변이 확인).
- 색은 계산해서 고른다: 글자 4.5:1, 막대·테두리 3:1. hover 상태까지 테스트로 보장.

더할 것:
- **KWCAG 2.2 대응 근거** — 국가표준 KS X OT0003:2022(4원칙·14지침·33검사항목)의 항목별로 각 컴포넌트가 무엇을 해 두었고
  사용하는 쪽이 무엇을 해야 하는지(예: 대체 텍스트 내용은 사용자 몫) 표로 정리한다.
  **"인증을 보장한다" 가 아니라 "대응 근거를 제공한다"** 로만 표현한다.
- 컴포넌트 문서마다 키보드 조작표·스크린리더 동작 메모.

### 3. 대표색 하나로 끝나는 테마 — "브랜드 색을 넣어도 접근성이 깨지지 않는다"

이미 있는 것: `createIntentColors(intent, hex)` 가 대표색 하나로 라이트·다크의 solid·hover·subtle·text·contrast 를 만들고
대비 4.5:1(hover 포함)을 테스트로 보장한다. CSS 변수 이름(`--bestow-*`)이 고정이라 CSS 만으로도 덮어쓸 수 있다.

더한 것 (2026-10-15):
- **테마 빌더 페이지** ([Storybook › Foundations › Theme Builder](https://dev-bestow.github.io/BestOW-UI/?path=/story/foundations-theme-builder--builder))
  — 색을 고르면 라이트·다크 미리보기 + 대비 리포트(intent 별 글자·hover·subtle·막대·포커스 링) + `createTheme(...)` 코드 복사.
  만들면서 밝은 브랜드 색의 포커스 링 대비 미달을 찾아 고쳤다 — "보장" 이 실제로 검사로 지켜진다는 사례.

### 4. 한글 타이포그래피 기본값 — "한국어로 만들면 확실히 다르다"

이미 있는 것: Pretendard 기본 글꼴, 표·목록의 `word-break: keep-all`, 한국어 기본 문구("닫기", "(새 창)", "이동 경로", "결과가 없어요").

더할 것: 전역 한글 줄바꿈 기본값, 한글에 맞춘 줄 간격 스케일 점검, 숫자 정렬(tabular) 기본, 기본 문구를 한곳에서 바꾸는 방법(다국어 대응).

## 다른 선택지와 비교

> 경쟁 제품 정보는 아래 출처에서 확인한 것만 적었다. 세부 기능 비교는 README·랜딩에 올리기 전에 각 문서에서 다시 확인한다.

| | BestOW UI | 글로벌 DS (MUI·Chakra·Mantine 등) | shadcn/ui | 한국 회사 DS |
|---|---|---|---|---|
| 한국 서비스 부품 | **기본 제공 (P6 목표)** | 없음 → 직접 구현 | 없음 → 직접 구현 | **(확인 필요)** |
| 브랜드 | 중립 — 대표색 하나로 교체, 대비 보장 | 테마 시스템 있음, 대비 확인은 사용자 몫 **(제품별 확인 필요)** | 직접 수정 | 해당 회사 브랜드 중심 |
| 접근성 근거 | 라이트·다크 axe CI + KWCAG 대응 문서(예정) | 제품마다 다름 | Radix 기반, 검사는 사용자 몫 | 제품마다 다름 |
| 스타일 방식 | vanilla-extract(런타임 0), RSC 사용 가능 | 제품마다 다름 | Tailwind | 제품마다 다름 |
| 문서 언어 | 한국어 우선 (npm README 는 영·한) | 영어 | 영어 | 한국어 |

참고한 한국 오픈소스 DS:
- **SEED (당근)** — Apache 2.0, 하나의 토큰 소스로 React·iOS·Android 등 멀티 플랫폼, Figma 연동, llms.txt·MCP 등 AI 연동 제공
  ([GitHub](https://github.com/daangn/seed-design), [소개 글](https://discuss.pytorch.kr/t/seed-llms-txt-mcp-ai/11462)).
- **Vapor UI (구름)** — `@vapor-ui/core`, MIT, 접근성·CSS cascade layer 를 원칙으로 함
  ([문서](https://vapor-ui.goorm.io/docs/getting-started/principles), [jsDelivr](https://www.jsdelivr.com/package/npm/@vapor-ui/core)).
- **Bezier (채널톡)** — `bezier-react`, 채널톡 전용으로 만들어져 확장성 한계로 재설계 진행 중이라는 이슈
  ([GitHub](https://github.com/channel-io/bezier-react), [이슈 #1578](https://github.com/channel-io/bezier-react/issues/1578)).

→ 이들과 **정면으로 겨루지 않는다.** 멀티 플랫폼·대규모 조직(SEED), 특정 서비스 브랜드(Bezier)와 달리
"내 서비스 브랜드로 바로 입혀 쓰는 한국 서비스 부품 + 검증된 접근성" 에 집중한다.

## 메시지 (README·Storybook 첫 화면용 초안)

- 제목: **한국 서비스를 위한 접근성 검증 디자인 시스템**
- 부제: 대표색 하나로 내 브랜드 테마를. 약관 동의부터 인증번호까지, 한국 서비스에 늘 필요한 부품을 기본으로.
- 근거 3줄:
  1. 모든 컴포넌트를 라이트·다크에서 자동 접근성 검사 (CI)
  2. 브랜드 색을 바꿔도 글자 대비 4.5:1 자동 보장
  3. 런타임 CSS 0, Next.js 서버 컴포넌트 지원, Button 하나 1.5 kB

## 성공을 어떻게 볼 것인가

- 한국 서비스 키트 각 부품: "직접 만들면 하루" 걸리는 것을 설치 후 10분 안에 쓸 수 있다(문서 예제 기준).
- npm 주간 다운로드, GitHub 스타·이슈(외부 사용자 질문이 생기는가).
- 접근성: 스토리 axe 위반 0 유지, KWCAG 대응 표가 모든 컴포넌트를 덮는다.

## 위험과 대응

| 위험 | 대응 |
|---|---|
| 한국 키트 부품이 서비스마다 요구가 달라 쓰기 어렵다 | 동작(headless)과 모양을 나누고, 흔한 옵션만 props 로. 직접 조합할 수 있게 하위 부품도 export |
| 접근성 문구가 과장으로 읽힌다 | "인증 보장" 금지, "대응 근거·자동 검사" 로만 표현. 수동 검사가 필요한 항목을 문서에 명시 |
| 외부 서비스 의존(우편번호 API 등) | 선택적 패키지/어댑터로 분리해 코어 번들에 넣지 않는다 |
| 작은 팀·개인 프로젝트라 "계속 관리될까" 신뢰를 얻기 어렵다 | 1.0 API 안정화(로드맵), 변경 기록·마이그레이션 문서, 자동 검사 공개 |
